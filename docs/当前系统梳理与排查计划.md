# 当前系统梳理与排查计划

更新时间：`2026-05-06`

## 1. 目标

当前项目已经从“本地日志搜索工具”演进为“本地 SSH 工作台”。

由于近期做了系统拆分，前端、网关、Electron 壳、共享协议层之间的边界变多，状态同步与接口契约更容易出现漂移。本文件用于先把系统真实功能面、模块边界、主链路和高风险断点梳理清楚，再作为后续排查 bug 的执行清单。

---

## 2. 当前系统真实结构

### 2.1 仓库分层

- `apps/extension`
  - React + Vite 前端工作台
  - 既服务浏览器访问，也服务 Chrome 扩展与 Electron 内嵌页面
- `apps/gateway`
  - 本地 Node 网关
  - 提供 HTTP API、WebSocket、SSH/SFTP、JumpServer、文件传输等能力
- `apps/electron`
  - 桌面壳
  - 负责窗口、托盘、打包、启动 gateway、桌面专属能力
- `packages/shared`
  - 前后端共享类型与协议

### 2.2 当前功能域

- 服务器管理
  - FinalShell 导入
  - Xshell 导入
  - 手动添加、编辑、删除服务器
  - 凭证保存与读取
  - 堡垒机 / JumpServer 路由配置
- 文件浏览与操作
  - 目录树、路径栏、筛选、排序、历史
  - 预览、保存、上传、下载、删除、重命名、压缩、解压
- 日志搜索
  - 单文件搜索
  - 异步搜索任务
  - 多文件搜索
  - 结果 tab、上下文模式、命中跳转、导出
- 大文件阅读
  - `meta`
  - `slice`
  - `line-context`
  - 命中跳转切片
  - 预读与缓存
- 实时与终端
  - `/ws/live`
  - `/ws/terminal`
  - JumpServer shell
  - 分屏终端
- 辅助能力
  - 录制
  - 传输记录
  - PiP / 独立窗口
  - toast
  - 快捷键

## 3. 前端真实边界

### 3.1 编排层

核心入口仍然是：

- `apps/extension/src/ui/App.tsx`

虽然大量逻辑已经拆到 hooks 和面板组件，但 `App.tsx` 仍然持有大量跨域状态，是当前前端的编排中枢。

### 3.2 已拆出的核心 hooks

- `useServerManagement.ts`
  - 服务器列表获取
  - 手动服务器增删改
  - workspace 与 server 之间的切换关系
- `useServerConnection.ts`
  - 凭证状态
  - 二跳配置
  - JumpServer 资产搜索
  - 连接测试
  - 连接成功后的目录拉取
- `useLogViewer.ts`
  - 目录读取
  - 文件打开
  - 搜索任务
  - 结果 tab
  - 切片导航
  - 行上下文
  - viewer 行为
- `useWorkspaceSessionManager.ts`
  - workspace 状态捕获
  - workspace 状态恢复
  - 切换时缓存与恢复控制
- `useFileOperations.ts`
  - 删除、重命名、移动、压缩、解压、预览、保存
- `useFileTransfer.ts`
  - 上传、下载、传输记录
- `useTerminalWindowManager.ts`
  - 终端独立窗口
  - Electron PiP / detached terminal 管理
- `useImportSettings.ts`
  - FinalShell / Xshell 导入
  - 导入路径与导入状态

### 3.3 前端最危险的耦合点

1. `serverId` 变化副作用过多
   - 会触发连接状态重置
   - 可能触发 terminal 停止
   - 可能触发 live follow 停止
   - 可能触发目录/文件/搜索结果清空

2. workspace 恢复链复杂
   - `workspaceSessionStatesRef`
   - `pendingWorkspaceActivationRef`
   - `restoringWorkspaceStateRef`
   - `skipServerSelectionResetRef`
   - `skipServerAutoConnectRef`

3. viewer 域职责过大
   - `useLogViewer` 同时覆盖目录浏览、文件打开、搜索任务、结果 tab、slice、line context、selection、reader rail

4. 宿主形态差异
   - 浏览器
   - Chrome 扩展
   - Electron 内嵌
   - Electron 独立 terminal/viewer 窗口

## 4. 网关真实边界

### 4.1 当前 `index.ts` 承担的职责

`apps/gateway/src/index.ts` 仍然是一个高密度入口文件，当前同时承接：

- 服务初始化
- 配置加载
- 导入策略装配
- HTTP API 注册
- `/ws/live`
- `/ws/terminal`
- 前端静态资源托管

### 4.3 网关最危险的耦合点

1. 入口文件过重
   - HTTP / WS / 静态托管都在 `index.ts`

2. 连接策略分支变多
   - 直连
   - 堡垒机入口
   - bastion target
   - JumpServer shell
   - JumpServer SFTP 虚拟路径

3. 搜索和 viewer 契约变复杂
   - `LogSearchResponse`
   - `LogSearchTaskResponse`
   - `LogSliceResponse`
   - `LogLineContextResponse`

4. 录制、live、terminal 都依赖 SSH 长连接或会话生命周期

## 5. 共享协议层变化

`packages/shared/src/index.ts` 相比最初版本，已经扩张出更多协议：

- `ServerConnectionKind`
- `ServerRouteConfig`
- `JumpServerAsset*`
- `LogSearchTaskResponse`
- `MultiFileLogSearch*`
- `SshTunnel*`
- `BatchCommand*`
- `LogLineContext*`
- `LogSliceResponse.fileSize`
- `LogSliceResponse.modifiedTime`

这意味着当前 bug 很可能来自：

- 前端按旧字段消费
- gateway 已返回新字段但前端没用
- 前端已依赖新字段但某些分支没返回

## 6. 已识别的漂移与风险

### 6.1 根脚本入口漂移

根目录 `package.json` 当前只剩：

- `build:extension`

但 `README.md` 仍在描述：

- `npm run dev:gateway`
- `npm run dev:extension`
- `npm run build`
- `npm run start:gateway`

这会直接影响：

- 新同学启动项目
- 自动化脚本
- 排障路径
- 文档可信度

### 6.2 文档口径可能落后于当前代码

优先关注：

- `README.md`
- `docs/拆分清单.md`
- `docs/架构与修改地图.md`

### 6.3 前端拆分不彻底

虽然 hooks 已拆，但 `App.tsx` 仍持有大量主状态，说明当前阶段更像：

- “逻辑外提了一部分”

而不是：

- “边界已经真正稳定”

## 7. 主链路梳理

### 7.1 启动链路

1. 启动前端 / gateway / Electron
2. `initializeWorkbench`
3. `checkLocalServiceHealth`
4. `fetchServers`
5. `fetchFinalShellSettings`

### 7.2 服务器工作流

1. 选择 server
2. `useServerManagement.selectServerById`
3. `useWorkspaceSessionManager.startWorkspaceActivation`
4. `serverId` 副作用触发 reset / restore
5. `fetchCredentialStatus`
6. `fetchServerRoute`
7. `testServerConnection`

### 7.3 文件工作流

1. 连接成功
2. `fetchDirectoryListing`
3. 目录树 / 文件表更新
4. `openEntry`
5. `fetchLogMeta`
6. `fetchLogSlice`

### 7.4 搜索工作流

1. 输入搜索条件
2. `runSearch`
3. `apiCreateSearchTask`
4. `apiPollSearchTask`
5. 结果进入 `results` / `resultTabs`
6. viewer 高亮 / jump / context mode

### 7.5 终端工作流

1. `ensureTerminalSessionId`
2. `openTerminalView`
3. `/ws/terminal`
4. Electron 下可 detached
5. workspace 切换时终端归属与 sessionId 恢复

## 8. 排查顺序

### 第一阶段：入口与宿主

目标：

- 确认项目真实启动方式
- 确认文档与脚本是否一致
- 确认浏览器 / Electron / 扩展三种宿主的入口是否一致

检查项：

- 根 `package.json`
- `apps/gateway/package.json`
- `apps/extension/package.json`
- `apps/electron/package.json`
- `README.md`

### 第二阶段：主工作流

目标：

- 先打通最核心链路：
  - `服务器选择 -> 连接测试 -> 目录浏览 -> 打开文件`

检查项：

- `useServerManagement`
- `useServerConnection`
- `useLogViewer.fetchDirectoryListing`
- `useLogViewer.openEntry`

### 第三阶段：日志主链

目标：

- 打通：
  - `搜索任务 -> 结果 tab -> 命中跳转 -> slice/line-context`

检查项：

- `useLogViewer.runSearch`
- `apiCreateSearchTask`
- `apiPollSearchTask`
- gateway `/api/logs/search/tasks`
- `jumpToSearchMatch`

### 第四阶段：状态恢复

目标：

- 确认 workspace 切换、自动连接、缓存恢复不会互相覆盖

检查项：

- `useWorkspaceSessionManager`
- `serverId` 相关 effects
- `pendingWorkspaceActivationRef`
- `skipServerSelectionResetRef`
- `skipServerAutoConnectRef`

### 第五阶段：扩展能力

目标：

- 在主链稳定后再排：
  - terminal
  - file transfer
  - recording
  - PiP
  - multi-file
  - batch exec

## 9. 第一批最值得优先验证的问题

1. 根脚本是否还能支持 README 里的启动方式
2. `serverId` 变化时是否会误清空本应恢复的 workspace 状态
3. 自动连接与 workspace 恢复是否存在竞态
4. `resultTabs` / `results` / `activeViewerTabId` 是否总能保持一致
5. `LogSliceResponse` / `LogSearchTaskResponse` 的字段是否所有分支都完整返回
6. bastion / jumpserver 分支下：
   - 连接测试
   - 目录浏览
   - 日志打开
   - live follow
   是否与 direct 分支保持同等契约
