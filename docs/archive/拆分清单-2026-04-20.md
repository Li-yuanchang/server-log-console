# Server Log Console — 拆分清单

当前状态：`App.tsx` 6025 行，`styles.css` 5498 行，`theme-modern.css` 2830 行。
一个文件承担了过多职责，改任何功能都要通读全局，修改成本持续上升。

这份清单的目标：**把改动限制在边界内**，而不是一次性全部重构。

---

## 1. 拆分原则

- **渐进式**：每一步可独立验证，不需要一次全改
- **按功能域收口**：每个 hook/模块只管一个域的状态与副作用
- **App.tsx 最终角色**：只做编排层，不直接持有业务状态
- **样式按域拆文件**：Vite 支持 CSS import，不需要全塞一个文件

### 2.2 Workspace Session 恢复逻辑（约 250 行，641–876）

当前问题：`buildWorkspaceSession`, `createDefaultWorkspaceSessionState`, `captureCurrentWorkspaceSessionState`, `storeWorkspaceSessionState`, `readWorkspaceSessionState`, `saveCurrentWorkspaceSessionState`, `applyWorkspaceSessionState`, `startWorkspaceActivation` 全部定义在 App 内部，依赖大量闭包状态。

拆分方案：

- 抽入 `useWorkspaceSession.ts`
- `applyWorkspaceSessionState` 改为接收一组 setter 而非闭包捕获
- 或使用 `useReducer` 统一管理 workspace 相关状态，`applyWorkspaceSessionState` 变成 dispatch

**前置契约**：拆分前必须先定义 `WorkspaceSessionState` 的快照序列化/反序列化契约（哪些字段持久化、哪些仅内存、跨 tab 恢复时的字段兼容策略），否则拆分后状态恢复行为不可验证。

**优先级**：**最高**。这是当前最复杂的隐式状态流。

## 5. 推荐拆分顺序

按"收益/风险比"排序，每步可独立验证：

### Phase 1：低风险、高收益

1. **类型定义移出 App.tsx** → `types.ts`
2. **纯工具函数移出 App.tsx** → 已有 `utils.ts` / `storage.ts`
3. **样式按域拆文件** — 不改逻辑，只改 import（**中风险**：CSS import 顺序即优先级逻辑，拆分后必须严格保持原有顺序）

### Phase 2：核心状态收口

4. **useWorkspaceSession** — 最复杂但收益最大
5. **useServerConnection** — 解耦 serverId 重置逻辑
6. **useSearchState + useSearchActions** — 搜索域独立

### Phase 3：功能域独立

7. **useFileBrowserState + useFileOperations** — 文件浏览域
8. **useLogViewerState + useLogReader** — 日志切片域
9. **useTerminalState + useTerminalActions** — 终端域

### Phase 4：收尾

10. **useTransferState** — 传输记录
11. **useDialogState** — 弹窗状态
12. **useElectronEnv + useViewerPip** — 宿主环境
13. **gateway index.ts 路由拆分**

---

## 6. 每步验证方式

- **Phase 1**：`npm run typecheck && npm run build` in apps/extension
- **Phase 2–3**：同上 + 手动验证 workspace 切换、搜索、文件浏览、终端
- **Phase 4**：同上 + 如涉及 gateway 则 `npm run typecheck && npm run build` in apps/gateway
- **最终**：`npm run release:mac` 走完整打包安装验证

## 8. 风险与注意事项

- **不要一次全改**：每个 hook 独立抽、独立验证
- **workspace 恢复逻辑最复杂**：建议单独一个 PR，充分测试切 tab / 恢复 / 跳板机场景
- **样式拆分是中风险**：CSS import 顺序即优先级逻辑，拆分后 `styles.css` 中的 `@import` 顺序必须严格对应原文件中的书写顺序，否则选择器覆盖关系会变
- **gateway 路由拆分注意依赖注入**：Express 路由回调中依赖的 service 实例需要通过闭包或参数传入
- **已抽出的子组件（FileBrowserGrid 等）不需要再拆**：它们已经是独立文件，问题在 App 传给它们的 props 太多
