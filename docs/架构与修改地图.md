# Server Log Console — 架构与修改地图

这份文档不是产品说明，而是给“要改代码的人”看的快速地图。

目标：

- 先判断一个需求应该落在哪个模块
- 提前识别影响面，避免只改表层
- 知道每类改动应该读哪些文件、跑哪些验证

---

## 1. 仓库总览

```text
server-log-console/
├── apps/
│   ├── electron/   # 桌面应用壳：窗口、托盘、预加载、打包脚本
│   ├── extension/  # React + Vite 前端 UI，也作为 Chrome 扩展前端
│   └── gateway/    # 本地 Node 网关：HTTP API + WebSocket + SSH/SFTP
├── packages/
│   └── shared/     # 前后端共享类型与协议
└── docs/           # 使用说明、归档、架构/修改地图
```

### 模块关系

```text
Electron 壳 / Chrome 扩展 / 浏览器
          │
          │ HTTP + WebSocket
          ▼
     gateway (本地服务)
          │
          │ SSH / SFTP
          ▼
      远程 Linux / 堡垒机 / JumpServer
```

### 判断落点的最短规则

- **改界面、交互、状态恢复**
  - 先看 `apps/extension`
- **改接口、SSH 行为、文件/日志处理**
  - 先看 `apps/gateway`
- **改请求/响应字段、共享类型**
  - 先看 `packages/shared`
- **改桌面窗口、托盘、打包、安装、桌面专属能力**
  - 先看 `apps/electron`

---

## 2. 各模块职责与核心入口

## 2.1 `apps/extension`：前端 UI 层

### 职责

- 渲染主界面
- 维护前端交互状态与本地持久化状态
- 通过 HTTP 调 gateway API
- 通过 WebSocket 收实时日志与终端流
- 承担 Electron 内嵌页面和 Chrome 扩展页面两种宿主形态

### 关键入口

- `apps/extension/src/main.tsx`
  - React 启动入口
- `apps/extension/src/ui/App.tsx`
  - 主应用编排层，绝大多数跨功能状态在这里汇总
- `apps/extension/src/styles.css`
  - 全局样式、经典布局样式
- `apps/extension/src/theme-modern.css`
  - modern 主题与现代化布局样式

### 重要子模块

- **搜索与结果**
  - `SearchQueryPanel.tsx`
  - `SearchProgressPanel.tsx`
  - `VirtualLogViewer.tsx`
- **文件浏览/文件操作**
  - `FileBrowserGrid.tsx`
  - `FileBrowserPathbar.tsx`
  - `FileContextMenu.tsx`
  - `FilePreviewDialog.tsx`
- **终端**
  - `TerminalWorkspace.tsx`
  - `TerminalAI.tsx`
  - `TerminalShortcuts.tsx`
- **设置/连接**
  - `ConnectionSettingsWorkspace.tsx`
- **传输记录**
  - `TransferHistoryDialog.tsx`
  - `TransferHistoryDropdown.tsx`
- **通用弹层**
  - `ModalDialogs.tsx`
  - `FeedbackOverlays.tsx`

### 这里最容易变复杂的点

- `App.tsx` 同时承接：
  - workspace tab/session 状态
  - server 选择与连接相关状态
  - 搜索条件与结果状态
  - 文件浏览状态
  - live follow / terminal / 弹窗状态
- 所以很多“看起来只是 UI 小改”其实会碰到缓存恢复、自动连接、跨 workspace 切换等隐式逻辑

---

## 2.2 `apps/gateway`：本地网关层

### 职责

- 暴露 HTTP API 与 WebSocket
- 管理服务器清单、凭证与本地配置
- 统一 SSH / SFTP / JumpServer 连接能力
- 执行日志搜索、实时 tail、文件浏览、文件传输、终端会话
- 在本地托管构建后的前端静态资源

### 关键入口

- `apps/gateway/src/index.ts`
  - 网关总入口
  - 路由装配
  - WebSocket 挂载
  - 静态资源托管

### 核心子域

#### `modules/servers`

职责：服务器来源、凭证来源、本地配置、导入策略。

核心文件：

- `server-registry.service.ts`
  - 内存态服务器清单聚合
- `local-config.service.ts`
  - 本地持久化配置的读写
- `credential-resolver.service.ts`
  - 解析凭证来源
- `strategies/finalshell-strategy.ts`
- `strategies/xshell-strategy.ts`
  - 导入策略

#### `modules/logs`

职责：日志搜索、文件浏览、大文件切片、远程命令与文件传输。

核心文件：

- `logs.service.ts`
  - 历史搜索、实时日志核心服务入口
- `log-search-task.service.ts`
  - 异步搜索任务与进度
- `ssh-executor.service.ts`
  - SSH 执行、跳板、JumpServer 相关连接能力
- `file-browser.service.ts`
  - 目录浏览
- `log-slice.service.ts`
  - 大文件 meta/slice/line context
- `file-transfer.service.ts`
  - 上传、下载、删除、改名、压缩、解压、保存、预览
- `command-builder.ts`
  - tail / search 命令构建
- `strategies/*`
  - 直连、堡垒机、JumpServer 等连接策略分流

#### `modules/terminals`

职责：终端 WebSocket 会话管理。

核心文件：

- `terminal-websocket.ts`
- `terminal-session-manager.ts`

### `index.ts` 中的关键职责分段

- **启动与服务初始化**
  - 初始化本地配置、服务器清单、凭证解析器、SSH 与日志服务
- **HTTP API**
  - `/api/servers/*`
  - `/api/import/*`
  - `/api/logs/*`
  - `/api/files/*`
- **WebSocket**
  - `/ws/live`
  - `/ws/terminal`
- **静态资源托管**
  - 若存在 extension 构建产物，则由 gateway 直接托管 UI

---

## 2.3 `packages/shared`：共享协议层

### 职责

- 定义前后端共享类型
- 固定 API 输入输出结构
- 降低 extension / gateway 之间字段漂移

### 核心入口

- `packages/shared/src/index.ts`

### 适合放这里的内容

- 请求/响应类型
- 共享枚举
- 共享基础模型

### 不适合放这里的内容

- 前端 UI 状态
- gateway 内部实现细节
- Electron IPC 专属结构

---

## 2.4 `apps/electron`：桌面壳层

### 职责

- 创建主窗口与托盘
- 暴露 preload / IPC 给前端
- 启动并探测 gateway
- 打包 extension 与 gateway 产物进入桌面应用
- 处理桌面专属能力：保存文件、定位本地路径、PiP 窗口、窗口置顶等

### 关键入口

- `apps/electron/main.cjs`
  - 主进程入口
- `apps/electron/preload.cjs`
  - 预加载桥
- `apps/electron/package.json`
  - 启动、打包、安装脚本

### 当前主流程

1. Electron `whenReady`
2. 创建菜单和托盘
3. 先加载本地 extension 构建产物到主窗口
4. 后台启动 gateway
5. 前端自行通过 health / API 建立可用状态

### 修改这里时要特别注意

- 打包脚本必须优先走 `package.json` 预设命令
- 启动环境需要规避 `ELECTRON_RUN_AS_NODE` 污染
- 改 `main.cjs` 时要考虑：
  - 开发态与打包态路径是否一致
  - gateway 是主进程内导入还是子进程回退
  - 窗口/托盘/IPC 是否受影响

## 3. 关键数据流 / 状态流

## 3.1 UI 请求链路

```text
React 组件 / App.tsx
    ↓
API 封装 / fetch / WebSocket
    ↓
gateway 路由 (index.ts)
    ↓
service / strategy / SSH executor
    ↓
远程机器 / 堡垒机 / JumpServer
```

### 读这个链路的经验

- 如果 **前端展示不对，但接口返回对**
  - 先查 `apps/extension`
- 如果 **前端请求参数对，但返回不对**
  - 先查 `apps/gateway/src/index.ts` 对应路由 + service
- 如果 **gateway 日志显示命令不对、路径不对、连接不对**
  - 先查 `modules/logs/*` 和 `ssh-executor.service.ts`

---

## 3.2 服务器与凭证数据流

```text
FinalShell / Xshell 导入
        ↓
import strategy
        ↓
local-config.service
        ↓
server-registry.service
        ↓
/api/servers
        ↓
前端 server 列表 / 当前 workspace 状态
```

### 高风险点

- 改服务器字段时，通常要联动：
  - `packages/shared/src/index.ts`
  - gateway 的导入/保存逻辑
  - extension 的展示与状态恢复逻辑

---

## 3.3 workspace / session 状态流

这是当前前端复杂度最高的区域之一。

### 主要特点

- workspace tab 切换不只是切一个 `serverId`
- 实际还会关联恢复：
  - 搜索条件
  - 连接状态展示
  - 路由/堡垒机配置
  - terminal / live follow / 文件浏览位置

### 结论

- 凡是涉及 workspace tab、session strip、server 选择、自动连接、连接设置弹窗的修改
  - **默认先读 `App.tsx`**
- 这类改动的风险通常不是 UI，而是：
  - 切 tab 时状态被重置
  - 异步请求返回串写到别的 tab
  - 自动连接覆盖了恢复态

---

## 3.4 实时日志与终端链路

### 实时日志

```text
前端 start live
   ↓
WS /ws/live
   ↓
ssh-executor / tail command
   ↓
socket chunk push
   ↓
前端 viewer / live panel
```

### 终端

```text
前端 terminal panel
   ↓
WS /ws/terminal
   ↓
terminal-session-manager
   ↓
SSH shell / resize / input
   ↓
前端 xterm.js
```

### 高风险点

- 断线重连
- 会话关闭清理
- detached / PiP 终端和 tab 切换之间的状态转移
- JumpServer 模式与直连模式的分支一致性

## 4. 常见需求应该从哪里下手

## 4.1 改主题、布局、样式

先看：

- `apps/extension/src/styles.css`
- `apps/extension/src/theme-modern.css`
- 具体组件 `.tsx`

注意：

- 先确认是 classic 主题、modern 主题，还是两者都要改
- 样式问题经常不在当前组件，而在全局主题覆盖
- 面包屑、toolbar、workspace strip、modal 这类区域容易被多处样式叠加

验证：

- `apps/extension`: `npm run typecheck`
- `apps/extension`: `npm run build`

---

## 4.2 改某个 UI 组件行为

先看：

- 对应组件文件
- `App.tsx` 中该组件的 props 来源
- 是否有 localStorage / workspace session 恢复逻辑

特别注意：

- 如果组件受当前 server / workspace / live state 驱动，不要只改渲染层

验证：

- `apps/extension`: `npm run typecheck`
- `apps/extension`: `npm run build`
- 手动验证对应交互路径

---

## 4.3 改 HTTP API / WebSocket 协议

先看：

- `packages/shared/src/index.ts`
- `apps/gateway/src/index.ts`
- extension 中对应调用点

标准顺序：

1. 先改 shared 类型
2. 再改 gateway 实现
3. 最后改 extension 消费逻辑

验证：

- `apps/gateway`: `npm run typecheck`
- `apps/extension`: `npm run typecheck`
- 必要时两边都 `build`

---

## 4.4 改日志搜索 / 切片 / 目录浏览

先看：

- `apps/gateway/src/modules/logs/logs.service.ts`
- `log-search-task.service.ts`
- `log-slice.service.ts`
- `file-browser.service.ts`
- `command-builder.ts`

如果同时涉及前端：

- 再看 `App.tsx` 和对应 viewer / query / file browser 组件

高风险点：

- 远程 shell 转义
- 文件路径在直连 / JumpServer 下格式不同
- 大文件切片和搜索结果跳转的 offset / line context 一致性

---

## 4.5 改上传 / 下载 / 预览 / 编辑 / 压缩解压

先看：

- `apps/gateway/src/modules/logs/file-transfer.service.ts`
- extension 中：
  - `FileContextMenu.tsx`
  - `FilePreviewDialog.tsx`
  - `TransferHistoryDialog.tsx`
  - `TransferHistoryDropdown.tsx`

高风险点：

- 大文件/长传输过程中的状态同步
- 前端显示成功但服务端流异常
- Content-Length / 提前 close / 中断重试

---

## 4.6 改服务器导入、凭证、堡垒机、JumpServer

先看：

- `apps/gateway/src/modules/servers/*`
- `apps/gateway/src/modules/logs/ssh-executor.service.ts`
- `packages/shared/src/index.ts`
- extension 中连接设置相关组件

高风险点：

- 凭证来源优先级
- `serverId` 不变但 route/credential 状态变化
- bastion / jumpserver / target server 的身份边界

---

## 4.7 改 Electron 桌面行为或打包

先看：

- `apps/electron/main.cjs`
- `apps/electron/preload.cjs`
- `apps/electron/package.json`
- 相关脚本：
  - `prepare-gateway.cjs`
  - `install-mac-app.cjs`
  - `run-clean-electron-env.cjs`
  - `afterPack.cjs`

高风险点：

- 开发态与打包态资源路径
- gateway 启动时机
- preload API 与前端调用约定
- macOS 安装/启动环境污染

验证：

- 优先使用 `apps/electron/package.json` 既有脚本
- 常见完整验证：`npm run release:mac`

---

## 5. 修改前先做的影响面检查

任何非纯样式改动，建议先回答这几个问题：

- **改动属于哪一层？**
  - extension / gateway / shared / electron
- **有没有共享字段变化？**
  - 如果有，shared 必须一起看
- **有没有跨 workspace/session 状态？**
  - 如果有，`App.tsx` 要检查恢复逻辑
- **有没有直连 / 堡垒机 / JumpServer 分支？**
  - 如果有，默认要检查两条路径
- **有没有浏览器模式 / Electron 模式差异？**
  - 如果有，要考虑宿主行为不同
- **这次最小验证闭环是什么？**
  - 只跑 extension build，还是必须走 Electron 打包安装

## 6. 推荐验证矩阵

## 6.1 只改前端 UI / 样式

在 `apps/extension`：

```bash
npm run typecheck
npm run build
```

适用场景：

- 样式
- 布局
- 纯展示文案
- 不改接口字段的组件行为

## 6.2 改 gateway 逻辑或 shared 类型

至少验证：

```bash
# apps/gateway
npm run typecheck
npm run build

# apps/extension
npm run typecheck
npm run build
```

适用场景：

- API 字段变更
- 日志搜索逻辑
- 文件传输逻辑
- SSH / JumpServer 行为

## 6.3 改 Electron 相关逻辑

优先使用预设脚本：

```bash
# apps/electron
npm run release:mac
```

适用场景：

- 主窗口、托盘、preload、IPC
- 网关启动/托管逻辑
- 打包安装验证

## 7. 当前仓库的高复杂度区域

这些区域后续如果继续膨胀，建议优先拆边界。

### 7.1 `apps/extension/src/ui/App.tsx`

问题：

- 聚合状态过多
- 很多 feature 共享同一层状态与副作用
- 改动容易互相影响

建议方向：

- 把 workspace/session 状态管理抽离
- 把连接状态与 server route 状态抽离
- 把搜索、文件浏览、终端拆成更清晰的 feature state 边界

### 7.2 `apps/gateway/src/index.ts`

问题：

- 路由装配、启动流程、WebSocket 逻辑都集中在一个文件
- 体量已大，不利于定位责任

建议方向：

- HTTP routes 按域拆分
- live / terminal WebSocket 装配单独抽文件
- 入口只负责初始化与挂载

### 7.3 样式层

问题：

- `styles.css` 和 `theme-modern.css` 体量都很大
- 组件局部样式与全局主题覆盖混杂

建议方向：

- 按功能区分段或拆文件
- 给 toolbar / workspace / modal / file browser 等区域建立更稳定的命名边界

---

## 8. 新需求落地时的建议流程

### 小改动

适合：

- 单组件 UI
- 单处样式
- 小范围文案/交互

流程：

1. 找到组件 + 样式入口
2. 检查 `App.tsx` 是否传入关键状态
3. 改完跑 extension typecheck/build

### 中改动

适合：

- 一个功能区联动前后端
- 新增一个接口字段
- 修状态恢复/切 tab 逻辑

流程：

1. 先画影响面
2. 从 shared → gateway → extension 顺序修改
3. 跑 extension/gateway 双边验证

### 大改动

适合：

- 模块重构
- Electron 宿主行为调整
- workspace / terminal / transfer 这类跨功能改造

流程：

1. 先列修改地图
2. 分批次提交，避免一次改太多层
3. 每一批都做可运行验证
4. 如涉及桌面壳，最后走 `release:mac`

## 10. 使用这份地图的方式

每次开始改之前，先用下面这个最小模板自检：

```text
目标：
落点：extension / gateway / shared / electron
影响面：
是否涉及 workspace 状态恢复：是 / 否
是否涉及直连与 JumpServer 分支：是 / 否
验证命令：
```

如果一个需求无法在 1 分钟内填出这 5 项，通常说明它还需要先做影响面梳理，不适合直接下手改。
