# 大日志切片计划

## 1. 目标

为 `server-log-console` 增加接近 EmEditor 的大日志阅读能力，重点解决超大日志文件的快速定位、按需读取和搜索跳转问题。

本期目标不是完整复制桌面编辑器，而是建立可持续演进的底层抓手：

- 文件元信息读取
- 按字节范围切片读取
- 前端按需展示
- 为后续命中跳转、虚拟滚动、上下文展开打基础

## 2. 核心原则

### 2.1 不整文件加载

前端永远不直接加载整份日志文件。所有超大文件查看都通过服务端切片完成。

### 2.2 搜索与浏览分离

- 搜索模式：服务端远程执行搜索命令，返回命中结果
- 浏览模式：服务端按 offset + length 返回日志切片

### 2.3 结果可落盘

搜索结果和实时片段已经支持导出。切片浏览后续也要支持将当前窗口导出成片段文件。

### 2.4 平台兼容优先

方案默认兼容 macOS / Linux / Windows 的本地 FinalShell 路径发现，同时 SSH 到 Linux 目标服务器执行日志命令。

## 4. P1 详细范围

### 4.1 后端接口

- `POST /api/logs/meta`
  - 输入：`serverId`、`filePath`
  - 输出：文件大小、修改时间、建议编码、是否可读

- `POST /api/logs/slice`
  - 输入：`serverId`、`filePath`、`offset`、`length`
  - 输出：实际读取范围、文本内容、是否到文件头/尾

### 4.2 切片策略

- 以字节范围为主，不以页码为主
- 服务端多读少量缓冲区，尽量按完整行裁切
- 默认支持文本文件和常见日志扩展名
- `.gz` 当前阶段仍以搜索优先，不做随机切片主能力

### 4.3 验证要求

- 类型检查通过
- 构建通过
- 文档同步更新

## 5. 风险与预案

### 风险一：UTF-8 多字节截断

预案：

- 第一版允许轻微字符边界瑕疵，但优先保证整体流程跑通
- 后续在切片接口中加入更稳的边界修正策略

### 风险二：目标服务器命令能力差异

预案：

- 优先使用 Python 读取文件元信息和切片
- Python 不可用时，后续增加 shell fallback

### 风险三：超大文件尾部追读体验不稳定

预案：

- P1 只实现静态切片
- 实时场景继续由 `tail -F` 负责

## 6. 里程碑出口标准

### P1 完成标准

- 能读取远程文件元信息
- 能按 offset 读取远程切片
- 前端可展示返回结果
- 文档留档完整

### P2 完成标准

- 用户可浏览前后切片
- 用户可快速查看文件头和文件尾
- 当前窗口可导出

### 当前进展补充

- 前端已提供切片偏移与长度输入框
- 已支持上一段、重新加载、下一段、尾部切片
- 已展示文件大小、更新时间、当前偏移和下一偏移
- 下一阶段重点转向“搜索命中与切片偏移联动”
